## 1. CARNET ARCHIVE July Reconciliation

**독립 재도출 방법**: `work/ecount-sales/2026-07.json`의 원본 1,343개
라인을, `scripts/monthly-brand-sales.mjs`의 `mergeOfflineBrandSales()`가
실제로 적용하는 것과 정확히 동일한 필터(코드를 직접 읽어 확인, 새
규칙을 만들지 않음)로 수작업 재현했다:

```
필터: line.isOfflineRevenue === true
      && Number.isFinite(salesAmount)
      && "2026-07-01" <= date <= "2026-07-31"
그룹핑: resolveIdentity({productName, brandGroup}, identityContext).brand.brandCode
수량: quantity 그대로 합산(음수 취소 라인도 그대로 포함 — 별도 취소 로직 없음)
주문수: {date}|{documentNo} distinct 집합의 크기(문서번호는 날짜 내에서만 고유)
```

**Online (Cafe24)**: 23,303,130원. 이 값은 이번 수리 코드가 전혀
건드리지 않는다 — `enrichMonthlyArchiveBrandSales()`가 넘기는
`brandSales` 입력을 `cloneBrand()`가 그대로 복제하고
(`onlinePaidAmount: paidAmount`), 병합 루프는 오프라인 라인에 대해서만
`+=`로 누적한다(스크립트 원문 확인). 재병합 전후로 CARNET의
`onlinePaidAmount` 필드가 정확히 23,303,130원으로 동일함을 직접
확인했다. **주의**: 이 값 자체를 Cafe24 라이브 API로 재조회해
재검증하지는 않았다(네트워크/인증 필요, 이번 read-only 세션 범위
밖) — 대신 "이번 수리가 이 값을 변경하지 않았다"는 것을 소스 코드
검사 + 전/후 필드 동일성 확인으로 증명했다. 이 값 자체는 애초에 이번
버그의 대상이 아니었다(원래 정상적으로 계산돼 있었음, plan §7).

**Offline (ECOUNT)**: 원본 라인 중 CARNET ARCHIVE로 resolve되는
라인은 **99개**(양수/음수 포함, 취소·재입고 페어 다수 포함 — 예:
07-04 COATED SKIRT PANTS IVORY +576,000/-576,000처럼 순감이 0이 되는
쌍도 존재), 순합계:

```
sum(salesAmount) = 20,854,700원
sum(quantity)    = 63개
distinct(date|documentNo) = 61건
```

**ONLINE + OFFLINE = TOTAL**:
```
23,303,130 + 20,854,700 = 44,157,830  ✓ (재병합 결과와 정확히 일치, 반올림 오차 없음)
```

이 독립 재도출은 실제 production `mergeOfflineBrandSales()`를
호출한 결과와도 정확히 일치했다(§3에서 63개 전 브랜드에 대해
0건 불일치로 재확인).

**이전 아카이브가 23,303,130원이었던 이유 / 정확히 어떤 구성요소가
빠졌었는가**: §4에서 확인하듯, 2026-07 아카이브는
`brandSalesBasis: "online_offline"` 플래그가 이미 설정돼 있었음에도
**오프라인 병합 결과가 사실상 전무했다** — CARNET뿐 아니라 오프라인
매출이 있던 **62개 브랜드 전부**의 오프라인 성분이 빠져 있었다(offline
매출 237,972,530원 전액 미반영). 즉 이전 아카이브의 23,303,130원은
"CARNET의 온라인 매출만 있고 오프라인 매출 20,854,700원 전액이
빠진 값"이며, 이는 CARNET 개별 문제가 아니라 **그 1회 빌드에서
오프라인 병합 단계 자체가 사실상 전체적으로 실패했는데 완료
플래그만 정상적으로 찍혔던 것**이다(root cause 정정, §4/§5).

## 2. TROUBLED WATERS July Reconciliation

같은 방법으로 독립 재도출:

```
Revenue: 2,414,200원
Units:   6개
Orders:  6건
AOV:     round(2,414,200 / 6) = 402,367원
Online:  0원 (이 브랜드는 온라인 카탈로그에 존재하지 않음 — 오프라인 전용)
Offline: 2,414,200원
```

**Units = 7 주장에 대한 정확한 원인 규명**: `work/ecount-sales/2026-07.json`
전체 1,343개 라인 중 `brandGroup === "TRO"` 이거나 productName이
"TROUBLED WATERS"에 매칭되는 라인을 **날짜/isOfflineRevenue 필터
전혀 없이** 전수 스캔한 결과도 정확히 **6건**이며, 전부
`quantity: 1`, 취소/음수 라인 전무, 중복 documentNo 전무(각기 다른
날짜의 서로 다른 전표)다. 즉:

- **원본 데이터에 7번째 라인은 존재하지 않는다** — 어떤 필터
  조합으로도(날짜 제한 여부, isOfflineRevenue 여부 무관) 6건 이상
  나올 수 없다.
- **수량 시맨틱 차이도 아니다** — 6건 모두 quantity 필드가 1이며,
  "수량 합"과 "라인 개수"가 우연히 같다(6=6). 다른 집계 방식(예:
  SKU 단위/사이즈 단위)을 적용해도 결과가 달라질 근거가 없다.
- **취소/환불 처리 때문도 아니다** — TROUBLED WATERS 6건 중
  취소·환불(음수 salesAmount 또는 음수 quantity) 라인은 0건이다
  (참고로 CARNET ARCHIVE는 실제로 다수의 취소/재입고 쌍이 있었다 —
  §1 — 이런 취소 패턴이 존재하는 브랜드도 있다는 사실 자체가
  "다른 브랜드와 혼동했을 가능성"의 한 단서였으나, TROUBLED WATERS
  라인 자체에는 해당 없음).
- **중복 ECOUNT 라인 때문도 아니다** — 6개 라인의 documentNo(1, 2,
  4, 8, 2, 18)는 서로 다른 날짜에 걸쳐 있어 중복이 아니며, 스냅샷
  파일 자체에도 정확히 6개 항목만 존재한다(파일을 두 번 읽거나
  합치치 않음, 단일 파일 단일 스캔).

**결론(단일 canonical 답변)**: **이전 진단의 Units = 7은 오기(수작업
집계/기록 오류)였다.** 이번 세션에서 독립적으로 4가지 방법
(①원본 라인 무필터 전수 스캔, ②production 필터 규칙을 그대로 적용한
수작업 재현, ③실제 `mergeOfflineBrandSales()` 직접 실행, ④실제
서버 API 응답 및 Chrome UI 렌더링 결과)으로 재확인했고 전부 정확히
6을 반환했다 — 데이터 자체에 7이 나올 수 있는 경로가 없다. 이는
이 세션에서 이미 한 번 발견해 기록한 유사 사례
(`NEXT-CROSS-BRAND-PARTIAL-PERIOD-diagnosis.md`의 "6,482,990 vs
6,481,990" 수작업 오기)와 같은 종류의 오류다.

## 3. Cross-Check Against Existing SAMPLAS Sales Semantics

새 규칙을 전혀 만들지 않았다는 근거:

- §1/§2의 독립 재도출은 `scripts/monthly-brand-sales.mjs`의
  `mergeOfflineBrandSales()` 소스를 그대로 읽고, 그 필터·집계 로직을
  손으로 재현한 것이다(다른 판정 기준을 도입하지 않음).
- 이 재현 결과를, 실제 production 함수를 그대로 호출한 결과 및
  라이브 서버 API 응답과 **1원 단위까지 정확히 대조**했다.
- **전수 대조**: 오프라인 매출이 있는 63개 코드(UNASSIGNED 포함)
  전부에 대해 "독립 재계산 offline 합계" vs "현재 아카이브에 저장된
  offlineSalesAmount"를 비교한 결과 **63개 전부 완전 일치, 불일치
  0건**이었다.
- **최상위 합계 정합성**: `sum(brandSales[].salesAmount)` =
  273,544,433원 = `archive.sales.totalSales.amount`(기존에 이미
  존재하던, 이번 수리와 무관하게 계산되는 최상위 집계) =
  `archive.sales.onlineSales.paidAmount`(35,571,903) +
  `archive.sales.offlineSales.offlineSalesAmount`(237,972,530). 이
  최상위 합계는 `mergeOfflineBrandSales()`가 전혀 관여하지 않는
  기존 별도 집계 경로에서 나온 값인데, 브랜드별 합계와 정확히
  일치한다 — 매출 보존(Revenue Preservation) 원칙이 이번 수리로도
  깨지지 않았다는 가장 강력한 교차검증이다.
- 취소/환불은 별도 로직 없이 원본 라인의 부호(양수/음수) 그대로
  합산되는 기존 방식 그대로다(CARNET 사례에서 다수 확인, §1) — 새
  취소 처리 규칙을 추가하지 않았다.
- Gift 라인 제외, QQQ 운영 품목그룹 제외 등 다른 기존 정책은
  `mergeOfflineBrandSales()` 자체가 이미 담당하며 이번 수리(freshness
  gating)는 그 함수의 내부 로직을 전혀 수정하지 않았다(직전 구현
  보고서 §3에서 이미 확인, 이번 세션에서 소스 재확인으로 재검증).

## 4. Archive Diff — work/monthly/2026-07.json

**"이전" 파일은 복구 불가능함을 먼저 밝힌다**: `work/`는 gitignore
대상이라 git 이력이 없고, `writeJsonAtomic()`은 임시파일+rename
방식이라 이전 버전 백업을 남기지 않는다. 로컬 Time Machine 스냅샷도
확인했으나(`tmutil listlocalsnapshots /`), 가장 최근 스냅샷
(2026-08-11 01:26)이 이 파일의 마지막 수정 시각(2026-08-12 00:18,
직전 세션의 Chrome QA 검증 단계에서 재기록됨)보다 이전이라 온전한
"이전 파일"을 다시 마운트해 확인하는 것은 이번 read-only 조사
범위에서 시도했으나 이 macOS 환경의 `tmutil`이 `mountsnapshot`
서브커맨드를 지원하지 않아 실패했다 — 더 깊이 파고들지 않고
대안으로 넘어갔다.

**대신 사용한 방법(수학적으로 유효함)**: `mergeOfflineBrandSales()`는
온라인 baseline 위에 오프라인을 **더하기만** 한다(대체 없음, §1/§3
소스 확인). 따라서 각 브랜드에 대해:

```
이전 값 = 현재 값 − (독립 재계산한 이번 오프라인 기여분)
```

이 식은 순수하게 덧셈 연산의 역산이며 새로운 가정을 도입하지 않는다
(UNASSIGNED 버킷은 온라인 미배분액 조정이 별도로 섞여 있어 이 역산
공식이 성립하지 않으므로 제외 — 아래 표에서 다룸).

  전체적으로 누락됐다는 것)의 결과다.

이번 검증으로 범위가 2개 브랜드에서 62개 브랜드로 크게 넓어졌다는
사실 자체는 커밋을 막을 이유가 아니다 — 오히려 freshness 수리가
애초에 왜 필요했는지(원래 알려진 것보다 훨씬 큰 손상을 이미 입고
있었던 아카이브)를 더 강하게 뒷받침하며, 재병합 메커니즘이 그
손상을 정확하게(0건 불일치로) 복구했음을 확인해준다.
