## I. Detector gaps and improvements (proposal, not implemented)

How this compares with PERSONSOUL, UNDER THE SIGN and PRAYING:
- `B0000COL` is the same root cause: a code minted by Marketing OS inside the Cafe24 namespace.
- It is at an earlier stage. Today's `classifyCodeReuse` / MINTED_CODE_COLLISION only runs when a pending candidate exists on the code, which means after Cafe24 has already issued it. So the detector cannot see this risk in advance.
- The 126 legacy codes are a different type: deleted Cafe24 brands. The rule cannot tell "deleted" apart from "never issued".

Proposed rules for `auditUnconfirmedCafe24Codes`:
1. **`CODE_AHEAD_OF_CAFE24`** (true risk):
   - Condition: Cafe24-format code, not live, and above the live maximum (ordered by code; Cafe24 is monotonic).
   - Action: flag P1 and raise it to P0 when it comes within N steps of the maximum. Recommend a re-key.
2. **`RETIRED_CAFE24_CODE`** (harmless legacy):
   - Condition: below the maximum, not live, no catalog products under the code, entry inactive.
   - Action: record only; do not create a pending item. Treat `externalCodes.cafe24.until` or a retired marker as confirmation.
3. **Confirmed identity** (valid):
   - Condition: live with a matching name or alias, or `externalCodes.cafe24.code` equals the code and `nameSource: confirmed`.
   - Action: skip.
4. **Name mismatch on a live code** (manual review):
   - Condition: live but the name differs, and there is no split metadata.
   - Action: classify through `classifyCodeReuse` (MINTED_CODE_COLLISION, CAFE24_CODE_REUSED or REVIEW_REQUIRED).
5. **Freshness:**
   - Recompute the audit on read from current Brand Master plus the cached Cafe24 list, or after every Brand Master write.
   - This prevents stale entries like the two in G.

## Detector hardening (2026-10-07, local commit, not deployed)

- **Old behaviour:** `auditUnconfirmedCafe24Codes` flagged every Cafe24-format code that was not live, or whose live name differed, as one undifferentiated `UNCONFIRMED_CAFE24_CODE` list (129 entries).
  - It never created pending candidates. Candidates come only from observed Cafe24/ECOUNT brand names.
  - But 127 of the 129 entries were noise: 126 deleted Cafe24 brands, plus 2 stale entries from before the splits. A real risk (B0000COL) looked the same as legacy residue.
- **New `cafe24CodeAudit`** (scripts/cafe24-code-reuse.mjs) classifies each entry whose *current* `brand_code` is Cafe24-format, in this order:
  1. VALID_CONFIRMED_CAFE24_IDENTITY: live owner whose name or alias matches, or a confirmed entry with `externalCodes.cafe24.code` equal to the code. Not listed; counted only.
  2. CODE_REUSE_SPLIT_REQUIRED: the live owner is a different identity. Carries the `classifyCodeReuse` classification (MINTED_CODE_COLLISION / CAFE24_CODE_REUSED / REVIEW_REQUIRED).
  3. CODE_AHEAD_OF_CAFE24: no live owner and the code is above the live maximum. It is PREEMPTIVE_REKEY_REQUIRED when there is no recorded Cafe24 ownership and no catalog products under the code.
  4. RETIRED_CAFE24_CODE: no live owner, below the maximum, inactive, 0 catalog products, no same-name live brand, and no ECOUNT products or sales lines for its names.
  5. REVIEW_REQUIRED: anything else, including when there is no live list to compare against.
- `formerCodes` are never treated as ownership, so split or re-keyed old codes (B0000BDG/BDJ/BDM old sides, B0000COL) are not audited again.
- **Pending scan `audit` block:**
  - `unconfirmedCafe24Codes`: actionable findings only.
  - `cafe24CodeSummary`: counts per status plus `cafe24MaxCode`.
  - `retiredCafe24Codes`: codes only, for debugging.
  - Nothing here creates candidates or writes Brand Master. Split, NEW auto-approval and REASSIGN rules are unchanged.
